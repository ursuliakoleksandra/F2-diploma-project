\## 1.2 Аналіз існуючих аналогів



\### 1.2.1 Home Assistant

Home Assistant



Архітектурний патерн. Монолітний застосунок на Python: ядро виконується в одному процесі з єдиним циклом подій asyncio, у межах якого функціонують event bus, state machine та service registry. Інтеграції завантажуються в цей самий процес, допоміжні сервіси розгортаються як контейнеризовані add-ons під керуванням Supervisor. Масштабування обмежується вертикальним зростанням одного вузла; горизонтальний розподіл навантаження та кластеризація не передбачені, а модель орієнтована на один об'єкт (одне домогосподарство).



Протоколи. REST API та WebSocket API для зовнішніх клієнтів і UI; MQTT та протоколи обладнання підключаються через інтеграції. Внутрішня взаємодія виконується через події в межах процесу без зовнішнього брокера повідомлень.



Стек даних. Компонент Recorder зберігає історію станів і подій у реляційній СУБД; за замовчуванням використовується SQLite, підтримуються MariaDB/MySQL та PostgreSQL. Для панелі Energy застосовується довгострокова агреговану статистика. Консистентність забезпечується локальними транзакціями СУБД; розподілені гарантії доставки відсутні.



Технічні обмеження. (1) Єдиний цикл подій: блокуюча операція в інтеграції збільшує затримку (Latency) обробки всіх подій. (2) SQLite за замовчуванням та зростання історії станів потребують налаштування очищення даних або переходу на зовнішню СУБД. (3) Відсутні гарантії доставки подій та механізми компенсації (Saga) для багатокрокових операцій. (4) Панель Energy виконує переважно ретроспективну аналітику; вбудоване прогнозування навантаження та оптимізація графіка приладів обмежені.



\### 1.2.2 OpenEMS

OpenEMS



Архітектурний патерн. Модульна платформа на Java, побудована на OSGi (Apache Felix), з розділенням на два середовища виконання: Edge (локальний контролер на gateway з детермінованим цикловим виконанням) та Backend (хмарний компонент, що обслуговує багато Edge). Edge здатний працювати автономно, що підвищує локальну відмовостійкість; масштабування кількості об'єктів визначається здатністю Backend підтримувати окреме з'єднання з кожним Edge.



Протоколи. JSON-RPC 2.0 поверх WebSocket (Edge – Backend – UI), локальний та хмарний JSON/REST API, MQTT-контролер, Modbus для взаємодії з обладнанням.



Стек даних. InfluxDB для часових рядів (локально на Edge та на Backend), Odoo для метаданих та облікових записів (XML-RPC). Конфігурація компонентів зберігається через OSGi Configuration Admin. Транзакційні гарантії та черги доставки між Edge і Backend у проаналізованій документації не виявлено; надійність запитів забезпечується таймаутами JSON-RPC.



Технічні обмеження. (1) Висока складність OSGi та модульної моделі підвищує поріг входження в розробку. (2) Backend тримає WebSocket-з'єднання з кожним Edge без проміжного брокера; релізи містять окремі оптимізації для великої кількості підключених Edge. (3) Запис у InfluxDB потребував явного механізму зворотного тиску (backpressure) через обмежений пул потоків. (4) Прогнозування споживання на основі методів машинного навчання не є ядром платформи; наголос зроблено на керуванні обладнанням (акумулятори, інвертори, зарядні станції).



\### 1.2.3 Emoncms

Emoncms



Архітектурний патерн. Модульний моноліт на PHP (Apache), доповнений фоновими воркерами (прийом MQTT, запис feed-ів, виконання сервісів). Redis використовується як буфер для зменшення дискових операцій запису. Масштабування вертикальне; горизонтальний розподіл компонентів не є цільовим сценарієм.



Протоколи. HTTP API для надсилання вхідних даних та читання feed-ів, MQTT для прийому телеметрії.



Стек даних. MySQL/MariaDB для метаданих, Redis для буферизації, власні файлові рушії часових рядів PHPFina (фіксований інтервал) та PHPTimeSeries (змінний інтервал). Асинхронний запис з буфера Redis на диск означає, що дані, які не були збережені, можуть бути втрачені при аварійному завершенні процесу.



Технічні обмеження. (1) Файлові рушії часових рядів не забезпечують реплікації та складних аналітичних запитів, доступних у СУБД часових рядів. (2) Фіксований інтервал PHPFina потребує визначення періодичності запису до початку збору даних. (3) Відсутні подієва модель, гарантії доставки та механізми розподілених транзакцій. (4) Прогнозування й оптимізація навантаження вбудованими засобами не реалізовані.

\### 1.2.5 Аналітичний висновок



Проведений аналіз показує, що розглянуті системи (Home Assistant, OpenEMS, Emoncms) орієнтовані переважно на локальне керування обладнанням і моніторинг окремого об'єкта, тому їхні архітектурні рішення мають обмеження для сценарію централізованої хмарної обробки телеметрії багатьох домогосподарств. Монолітна структура Home Assistant та Emoncms із вертикальним масштабуванням, єдиний цикл подій asyncio, у якому блокуюча операція збільшує Latency обробки всіх подій, а також асинхронний запис через буфер Redis без гарантій збереження даних при аварійному завершенні не забезпечують відмовостійкість і передбачувану пропускну здатність за зростання кількості джерел. В OpenEMS підтримка окремого WebSocket-з'єднання між Backend і кожним Edge без проміжного брокера повідомлень потребує додаткових оптимізацій продуктивності та механізмів зворотного тиску. Жодне з розглянутих рішень не реалізує гарантованої доставки подій, розподілених транзакцій із компенсацією (Saga) та вбудованого прогнозування навантаження на рівні платформи.



Обрана архітектура усуває ці обмеження. Використання Apache Kafka з партиціонуванням за ідентифікатором будинку забезпечує горизонтальне масштабування прийому даних і розв'язує producer та consumer; Transactional Outbox і ідемпотентні консюмери гарантують доставку at-least-once без дублювання ефектів; Dead Letter Queue та Resilience4j локалізують відмови окремих компонентів. Розділення моделей запису й читання (CQRS) з використанням TimescaleDB дозволяє виконувати аналітичні запити над часовими рядами без навантаження на конвеєр прийому, а JWT з RBAC та ізоляцією даних будинків забезпечує багатооб'єктну експлуатацію. Автоматизований конвеєр CI/CD зі SonarQube, Trivy і Gitleaks формалізує контроль якості та безпеки.



Прийняті рішення мають компроміси: подієво-орієнтована взаємодія вносить eventual consistency між write- і read-моделями, а розподілена архітектура підвищує операційну складність порівняно з монолітом. Ці ризики компенсуються визначеними цільовими показниками (SLO), спостережністю (Prometheus, Grafana) та експериментальною перевіркою відмовостійкості.

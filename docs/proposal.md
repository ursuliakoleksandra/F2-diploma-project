Пропозиція до кваліфікаційної роботи бакалавра

Спеціальність: F2 Інженерія програмного забезпечення
Версія: 2.0 

1. Назва проєкту
Подієво-орієнтована система прогнозування та оптимізації енергоспоживання житлових будинків із автоматизованим контролем якості та безпеки

2. Актуальність і постановка проблеми
Пікові навантаження в житловому секторі підвищують вартість електроенергії та навантаження на мережу. Наявні рішення зазвичай обмежуються візуалізацією споживання без прогнозування, виявлення аномалій і планування роботи приладів. Окрема інженерна проблема — надійна обробка потоків телеметрії від багатьох будинків за умов часткових відмов компонентів.

Мета: спроєктувати, реалізувати та розгорнути в хмарі відмовостійку систему моніторингу, прогнозування й оптимізації енергоспоживання, що відповідає визначеним SLO та вимогам безпеки.

Завдання:
Сформулювати функціональні, нефункціональні та безпекові вимоги; визначити SLI/SLO.
Спроєктувати архітектуру (C4, ADR) та обґрунтувати межі сервісів і патерни взаємодії.
Реалізувати конвеєр прийому телеметрії на Apache Kafka з гарантіями доставки та ідемпотентності.
Реалізувати патерни CQRS, Transactional Outbox і Saga.
Розробити модулі прогнозування, виявлення аномалій і оптимізації навантаження; порівняти методи за метриками точності.
Забезпечити відмовостійкість (circuit breaker, retry, DLQ) та перевірити її експериментально.
Побудувати CI/CD-конвеєр із контролем якості й безпеки (SAST, SCA, secrets scanning, container scanning, quality gate).
Розгорнути систему в хмарі, налаштувати метрики, дашборди й алерти.
Провести навантажувальне тестування (k6) та оцінити відповідність цільовим показникам.

Об'єкт дослідження: процеси збору, обробки та аналізу телеметрії енергоспоживання житлових будинків.
Предмет дослідження: архітектурні рішення та інженерні практики побудови надійної, безпечної й масштабованої системи прогнозування та оптимізації енергоспоживання.

3. Опис продукту
Платформа приймає телеметрію від пристроїв будинків, зберігає її як часові ряди, прогнозує навантаження, виявляє аномалії та формує плани зсуву роботи керованих приладів для зниження піку. На етапі розробки дані генерує симулятор, що відтворює різні профілі споживання та рівні навантаження без фізичного обладнання.

4. Архітектура
Тип: подієво-орієнтована сервісна архітектура з асинхронним обміном через Apache Kafka, REST API для клієнтів та розділенням моделей запису й читання (CQRS).

Компоненти:
simulator — генерація телеметрії для множини будинків;
ingestion-service — прийом, валідація та збереження подій;
api-service — автентифікація, реєстр пристроїв, read-модель і REST API;
forecasting-service (Python) — прогнозування та виявлення аномалій;
optimization-service — планування навантаження та оркестрація Saga;
web-client — аналітична панель.

Ключові рішення:
Kafka з партиціонуванням за ідентифікатором будинку;
Transactional Outbox для атомарної публікації подій;
Saga (оркестрація) для застосування плану оптимізації з компенсаційними діями;
ідемпотентні споживачі, Dead Letter Queue, retry з exponential backoff;
ізоляція даних між будинками на рівні авторизації та запитів.

5. Функціональні можливості
Моніторинг поточного та історичного споживання будинку й пристроїв.
Реєстр пристроїв: параметри, стан, потужність, графіки використання.
Прогнозування навантаження з урахуванням історії та часових ознак.
Виявлення аномалій надмірного або нетипового споживання.
Оптимізація навантаження: план зсуву роботи приладів з урахуванням ліміту потужності та тарифних зон.
Аналітична панель: стан, історія, прогнози, аномалії, результати оптимізації.
Мультибудинковість із розмежуванням доступу на основі ролей.

6. Нефункціональні вимоги (цільові SLO)
Характеристика	Цільовий показник
Пропускна здатність прийому	≥ 500 повідомлень/с
Затримка API (p95)	< 300 мс
Відновлення після відмови сервісу (MTTR)	< 60 с
Втрата повідомлень при відмові консюмера	0 (at-least-once + ідемпотентність)
Похибка прогнозу (MAPE)	≤ 15%
Зниження пікового навантаження (симуляція)	≥ 10%
Покриття тестами доменного шару	≥ 70%
Критичні вразливості в образах	0
Technical Debt Ratio (SonarQube)	≤ 5%

8. Життєвий цикл та автоматизація
CI/CD-конвеєр: збірка → модульні тести → інтеграційні тести (Testcontainers) → SonarQube, Gitleaks, Dependency-Check → збирання образів → Trivy → публікація в реєстр → автоматичне розгортання на хмарну VM → k6 smoke-тест. Збірка блокується через quality gate при порушенні порогів якості й безпеки.

9. Очікувані результати
працездатна система в хмарі з відкритим кодом і документованим API;
архітектурна документація (C4, ADR) з обґрунтуванням рішень;
порівняння методів прогнозування за метриками MAE, RMSE, MAPE;
звіти навантажувального тестування та відмовних експериментів;
автоматизований конвеєр якості й безпеки та дашборди моніторингу;
пояснювальна записка.

10. Можливе розширення
Kubernetes + Helm, розподілений трейсинг (OpenTelemetry), реплікація PostgreSQL, інтеграція з реальними лічильниками через MQTT, canary-релізи.
